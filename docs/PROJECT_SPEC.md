# Merchant Pulse — Project Specification

**Version:** 0.3  
**Status:** Approved implementation baseline  
**Project:** UNIVESP Projeto Integrador IV

## 1. Purpose

Merchant Pulse is an interactive e-commerce analytics application for small businesses. Its purpose is to organize navigation and sales information, make the purchase journey measurable, and support decisions through understandable indicators and analytical outputs.

The project is not intended to replace an e-commerce platform or become a full enterprise resource planning system. Its scope is the analysis and visualization of data generated by an e-commerce operation.

The academic report establishes the central problem: small e-commerce businesses may have navigation and sales information dispersed across different tools, making it difficult to identify purchase-journey bottlenecks and make informed decisions.

## 2. Project objectives

### 2.1 General objective

Develop a computational solution based on data analysis to support the identification of purchase-journey bottlenecks and the improvement of the user experience in a small e-commerce business.

### 2.2 Technical objectives

1. Build a reproducible e-commerce dataset with realistic relationships and sufficient volume for data analysis.
2. Implement a data ingestion and preprocessing pipeline.
3. Define and calculate consistent e-commerce indicators.
4. Present the five-stage purchase funnel interactively.
5. Analyze product, category, and customer-navigation patterns.
6. Implement a supervised machine-learning workflow for demand forecasting.
7. Implement a simulated IoT telemetry ingestion and monitoring workflow.
8. Provide an interactive dashboard with dynamic filters and visualizations.
9. Validate data quality, metric calculations, model performance, and application behavior.

## 3. Scope and exclusions

### 3.1 Included

- E-commerce navigation and sales analytics.
- Five-stage purchase funnel.
- Revenue, order, conversion, abandonment, and average-order-value indicators.
- Product and category performance.
- Customer behavior analysis using aggregated or pseudonymous information.
- Data ingestion and preprocessing reports.
- Simulated warehouse IoT telemetry.
- Supervised category-level demand forecasting.
- Interactive charts, filters, and exports.
- Dashboard authentication and user management.
- A simple store relationship in the data model.

### 3.2 Excluded

- Building or replacing the e-commerce storefront.
- Payment processing.
- Operational order fulfillment.
- Inventory management or stock movement operations.
- Physical IoT sensor installation.
- Complex multi-tenant SaaS infrastructure.
- Consumer account management.
- Marketing campaign execution or automated messaging.
- Claims that synthetic results represent actual partner-company performance.

Stock values may be displayed as read-only snapshots if the input dataset contains them. Merchant Pulse does not manage stock or perform inventory transactions.

The initial demonstration uses one store. Additional store records are supported by the model, but the first release does not require complex tenant provisioning or subscription management.

## 4. Data sources and provenance

### 4.1 E-commerce dataset

The initial e-commerce dataset is generated by a reproducible Python program.

The generator must create related records for:

- Products and categories.
- Visitor sessions.
- Navigation events.
- Orders and order items.
- Devices and traffic sources.
- Promotions and calendar effects.

The generated event sequence should reflect plausible purchase behavior:

`session → product view → cart addition → checkout initiation → completed order`

Not every session must reach every stage. Abandonment and non-conversion are essential characteristics of the dataset.

The initial target is approximately two years of simulated activity. Indicative volumes are 300,000–500,000 sessions, 2–5 million events, 50,000–100,000 orders, and 100–200 products. These targets must be benchmarked and adjusted to maintain internal consistency.

The generator must support a fixed random seed, configurable volume and date ranges, batch generation, and deterministic relationships between records.

The dataset is synthetic and must be identified as such.

### 4.2 IoT telemetry

IoT is represented through a software simulator. Physical sensors are not required.

The simulated context is warehouse environmental and operational monitoring. Each device generates timestamped measurements of:

- Temperature (°C).
- Relative humidity (%).
- Energy consumption (kW).

Initial configuration:

- 10 simulated devices.
- One measurement every five minutes.
- 180 days of simulation.
- 518,400 total readings.

The simulator should support plausible measurement variation and occasional abnormal readings. The values and thresholds are demonstration parameters, not certified safety or engineering limits.

The telemetry is simulated and must be labeled accordingly.

## 5. Data science requirements

### 5.1 Processing workflow

The preprocessing workflow must be reproducible and traceable:

1. Ingest source files or generated records.
2. Validate required columns, data types, and structural constraints.
3. Inspect missing values and define treatment rules.
4. Identify and remove duplicates.
5. Detect impossible, inconsistent, or invalid values.
6. Classify variables by measurement scale.
7. Transform data and create analytical features.
8. Validate the processed dataset.
9. Record processing statistics and quality results.

For each import or processing run, record at least:

- Number of records read.
- Number accepted.
- Number rejected.
- Number corrected, when applicable.
- Number of duplicates removed.
- Validation errors and warnings.

Do not silently discard invalid records. Rejection and correction rules must be documented.

### 5.2 Statistical variable classification

Before applying statistical summaries, variables must be classified as:

- Qualitative nominal.
- Qualitative ordinal.
- Quantitative interval.
- Quantitative ratio.

Examples:

| Variable           | Classification             | Appropriate analysis                       |
| ------------------ | -------------------------- | ------------------------------------------ |
| Product category   | Qualitative nominal        | Frequency, proportion, mode                |
| Traffic source     | Qualitative nominal        | Frequency, proportion, mode                |
| Device type        | Qualitative nominal        | Frequency, proportion, mode                |
| Order status       | Qualitative nominal        | Frequency, proportion, mode                |
| Priority level     | Qualitative ordinal        | Frequency and meaningful ordinal summaries |
| Temperature        | Quantitative interval-like | Mean, median, standard deviation, range    |
| Relative humidity  | Quantitative ratio         | Mean, median, standard deviation, range    |
| Energy consumption | Quantitative ratio         | Mean, median, standard deviation, range    |
| Units sold         | Quantitative ratio         | Sum, mean, median, dispersion              |
| Revenue            | Quantitative ratio         | Sum, mean, median, dispersion              |

Identifiers, IDs, and numeric encodings of nominal categories must not be treated as continuous numerical variables.

### 5.3 Large-scale processing

The project must demonstrate that its data pipeline can handle meaningful data volumes.

- Generate records in batches.
- Process large files in chunks where appropriate.
- Avoid loading all raw data into memory without justification.
- Use database aggregation for suitable analytical queries.
- Consider Parquet for intermediate analytical datasets.
- Measure execution time and memory use during representative workloads.
- Document any sampling, including its purpose, method, size, and limitations.

Sampling must not be used to conceal the actual data volume or to make unsupported claims about full-dataset performance.

## 6. E-commerce analytics definitions

### 6.1 Purchase journey

The funnel contains five stages:

1. Visit.
2. Product view.
3. Cart addition.
4. Checkout initiation.
5. Completed order.

The funnel counts distinct visitor sessions that reached each stage, not raw event records.

A session can produce multiple events of the same type. Each stage is counted at most once per session for funnel purposes.

Stage progression must be chronologically valid. A session should not be considered to have reached a later stage before the relevant preceding stage.

For the main funnel, sessions are attributed to their start date. This creates a session-cohort interpretation: a session belongs to the date on which it began, even if some events occurred later.

### 6.2 Revenue and order definitions

Only orders with the following statuses contribute to recognized sales revenue:

- `PAID`
- `SHIPPED`
- `DELIVERED`

The following statuses are excluded:

- `PENDING`
- `CANCELLED`
- `RETURNED`

Revenue is attributed to the order creation date, using the store's configured timezone.

Revenue and funnel conversion are separate analytical concepts. A session can generate multiple orders, and order creation may occur at a different time from session start. Therefore, the number of eligible orders must not be used as a direct substitute for the number of converted sessions.

### 6.3 Core indicators

| Indicator                | Definition                                                                                                      |
| ------------------------ | --------------------------------------------------------------------------------------------------------------- |
| Visits                   | Distinct sessions that reached the visit stage                                                                  |
| Product-view rate        | Sessions with product views ÷ sessions with visits                                                              |
| Cart-addition rate       | Sessions with cart additions ÷ sessions with product views                                                      |
| Checkout-initiation rate | Sessions with checkout initiation ÷ sessions with cart additions                                                |
| Session conversion rate  | Sessions with a completed order ÷ eligible visit sessions, with session-to-order attribution explicitly defined |
| Checkout abandonment     | 1 − (sessions with completed orders after checkout ÷ sessions that initiated checkout)                          |
| Eligible orders          | Orders with paid, shipped, or delivered status                                                                  |
| Recognized revenue       | Sum of eligible order totals under the documented order-value definition                                        |
| Average order value      | Recognized revenue ÷ eligible order count                                                                       |

If session-to-order attribution is unavailable or ambiguous, the application must not label `eligible orders ÷ visits` as an exact session conversion rate. It may show an order-to-session ratio with an explicit label and explanation.

Product-level sales and revenue must use eligible orders. Product views and cart additions may be analyzed separately from completed sales.

## 7. Machine-learning specification

### 7.1 Problem definition

The selected machine-learning task is supervised regression.

The model predicts the number of units sold per product category per day. The forecasting horizon should support next-day and next-week demand analysis.

This target is aligned with the project's e-commerce decision-support purpose and provides a measurable numerical outcome.

### 7.2 Features

Initial candidate features:

- Product category.
- Day of week.
- Month.
- Weekend indicator.
- Promotion indicator.
- Sales lag of 1 day.
- Sales lag of 7 days.
- Sales lag of 14 days.
- Rolling mean of 7 days.
- Rolling mean of 28 days.

All lag and rolling features must use information available before the prediction timestamp. Future information must never leak into training features.

Categorical variables must be encoded appropriately. Category identifiers must not be interpreted as continuous measurements.

### 7.3 Models

- Baseline: seasonal-naive forecast using the corresponding day from the previous week.
- Main candidate: `HistGradientBoostingRegressor` from scikit-learn.

The model must be trained through a reproducible Python pipeline. Hyperparameters should be selected using training and validation data only.

### 7.4 Evaluation

Use chronological data splitting:

- 70% training.
- 15% validation.
- 15% test.

The exact date boundaries must be recorded. Random splitting is not appropriate for this time-series forecasting task.

Metrics:

- MAE — Mean Absolute Error.
- RMSE — Root Mean Squared Error.
- R² — coefficient of determination.

Compare the model against the seasonal-naive baseline. Inspect training and validation performance for overfitting or underfitting. The final test set must remain separate from model selection.

Do not claim a model is useful merely because it has a non-zero R². Interpret the errors in the context of the target scale and baseline performance.

### 7.5 Dashboard behavior

The Demand Forecasting module should support:

- Category selection.
- Forecast horizon selection.
- Historical sales visualization.
- Forecast visualization.
- Actual-versus-predicted comparison where actual values exist.
- MAE, RMSE, and R² display.
- Baseline-versus-model comparison.

The interface must identify the model version and the date through which training data was available. Precomputed forecasts must be labeled as precomputed. The application must not imply real-time model execution unless that capability is actually implemented.

## 8. IoT specification

The IoT simulator sends measurements through HTTP to a Next.js API route.

The API must:

- Validate device identity and measurement fields.
- Validate timestamps and numeric ranges.
- Reject malformed or invalid payloads.
- Prevent duplicate ingestion.
- Persist telemetry separately from e-commerce navigation events.
- Return an appropriate response to the simulator.

The IoT Monitoring module should provide:

- Device selection.
- Latest readings.
- Temperature, humidity, and energy time series.
- Date-range filtering.
- Device comparisons.
- Threshold-based abnormal-reading indicators.
- A multivariate view where useful.

Thresholds are configurable demonstration parameters. They must not be represented as certified regulatory or safety limits.

## 10. Dashboard modules

### Overview

Displays the most relevant business indicators, comparisons with the previous period, daily trends, funnel summary, product performance, and rule-based recommendations.

Recommendations must be explainable and based on defined rules or measured deviations. They must not be presented as machine-learning outputs unless generated by a documented model.

### Sales Funnel

Displays the five purchase stages, session counts, conversion rates, and losses between stages. Supports period and relevant segment comparisons.

### Products & Performance

Displays product and category rankings, views, cart additions, eligible orders, conversion indicators, and revenue. Stock information is optional and read-only.

### Product Detail

Displays a selected product's performance over time, including navigation interest and eligible sales.

### Customer Behavior

Displays aggregated patterns by day, hour, device, and traffic source. It may distinguish new and returning pseudonymous visitors when the underlying data supports that classification.

### Data Sources & Pipeline

Displays source configuration, import history, processing status, record counts, and quality reports.

### IoT Monitoring

Displays simulated device measurements, time-series charts, comparisons, and abnormal-reading indicators.

### Demand Forecasting

Displays category-level forecasts, historical values, forecast horizons, model metrics, and baseline comparisons.

### Settings

Manages dashboard users, store settings, data-source configuration, indicator targets, and thresholds. Administrative settings are restricted to the ADMIN role in the initial release.

## 11. Authentication and authorization

Dashboard authentication is separate from visitor tracking.

Roles:

- `ADMIN`
- `MANAGER`
- `ANALYST`

The authentication design follows the established approach used in the PI-II application, adapted to Merchant Pulse:

- Password hashes are stored, never plaintext passwords.
- Session tokens are generated securely.
- Only token hashes are stored in the database.
- Sessions have expiration timestamps.
- Password reset tokens have expiration and usage state.
- User activity can be disabled.
- Store scope is enforced in application queries.

Initial permissions:

| Capability                           | ADMIN |      MANAGER | ANALYST |
| ------------------------------------ | ----: | -----------: | ------: |
| View analytics                       |   Yes |          Yes |     Yes |
| View IoT monitoring                  |   Yes |          Yes |     Yes |
| View demand forecasts                |   Yes |          Yes |     Yes |
| Export reports                       |   Yes |          Yes |     Yes |
| Manage data sources                  |   Yes |          Yes |      No |
| Manage users                         |   Yes |           No |      No |
| Change store settings                |   Yes |           No |      No |
| Change global targets and thresholds |   Yes | Configurable |      No |

Permissions should be enforced server-side, not only by hiding interface elements.

## 12. Privacy and data protection

The application must not collect or expose consumer names, emails, phone numbers, or full addresses.

Visitor and customer identifiers should be pseudonymized through hashes where necessary. Hashing does not automatically make data anonymous, so access and retention must still be controlled.

Exports must contain only the information needed for analysis and must exclude consumer personal information.

## 13. Acceptance criteria

The project is considered technically complete when:

- The generator produces reproducible, internally consistent e-commerce records at the documented scale.
- The IoT simulator produces the documented volume of valid telemetry.
- The ingestion pipeline validates, records, and deduplicates data.
- Preprocessing decisions and data-quality results are traceable.
- Variable types are correctly classified before statistical analysis.
- Funnel and revenue calculations follow the definitions in this specification.
- The demand model is evaluated against the seasonal-naive baseline using chronological splits.
- Model metrics and limitations are documented.
- The dashboard offers working interactive filters and visualizations.
- IoT readings and demand forecasts are accessible through the interface.
- Authentication and authorization are enforced on protected routes.
- Tests cover critical calculations, ingestion, and model preprocessing.
- Academic documentation accurately describes synthetic and simulated data.
